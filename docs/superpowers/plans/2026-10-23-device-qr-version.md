# 设备二维码版本与后端分流

用户已确认：旧设备继续访问旧后端，新设备访问新后端；二维码增加 `v`，缺省为 `0`。

最终支付范围：v0 保持原支付协议与已购行为，旧后端不更新；v1 使用新增文件价格、文件订单绑定和服务端解锁确认，只对新后端部署配套接口。

| 二维码 | 解析版本 | API |
| --- | --- | --- |
| `https://w.4mr.cn/t?k=TOKEN` | 0 | `https://x.4mr.cn/v2` |
| `https://w.4mr.cn/t?k=TOKEN&v=0` | 0 | `https://x.4mr.cn/v2` |
| `https://w.4mr.cn/t?k=TOKEN&v=1` | 1 | `https://checkin.voxel.cn/api/v2` |

版本是二维码协议标记，与设备上报的 `device.version` 分开。Token 格式沿用后端的 1 个英文字母加 32 个十六进制字符。不允许二维码提供任意 API 地址；非法及暂不支持的版本提示错误。

没有二维码的普通启动，在首次使用时沿用当前默认新 API，之后恢复最近一次扫码选择的后端，以便记录和用户页继续访问该设备所属后端。开发构建可用已有 `VITE_API_URL` 覆盖 v1 地址；v0 固定使用旧 API。

- [x] 解析工具先红后绿：无版本默认 0、显式 0/1、参数顺序、编码、错误输入及构建回环。
- [x] 页面和路由先红后绿：微信 `q` 入口、内置扫码、重启后版本保留及先选后端再登录。
- [x] 登录和请求：按 API 隔离缓存、登录单飞与 401 恢复；旧未分域凭据来源不明，升级后重新微信登录。
- [x] 云存储：按 API 隔离 STS 与 SDK，旧操作和回调始终使用原 API。
- [x] 页面及支付：录制、记录、设备分页、场景、文件与订单固定操作开始时的 API。
- [x] 支付按版本分支：v0 不调用新增文件详情/解锁接口，兼容原下单字段与旧版已购缓存；v1 保留服务端价格和解锁校验，完全忽略本地已购标记。
- [x] 验证：全量测试、类型检查、ESLint、微信/H5 构建与两种版本的 CommonJS 产物冒烟。

最终支付分支验证：35 个测试文件、495 项全部通过；`pnpm run tsc`、只读 ESLint、微信及 H5 构建通过。`node scripts/verify-mp-build.cjs` 在 v0、v1 执行文件列表、401 恢复、资料及各自支付协议，并验证 v1 拒绝缺少服务端解锁的 SUCCESS，共 9 项通过，使用模拟传输实际执行编译后的业务模块。独立复核未发现确定阻塞。

微信开发者工具重新打开构建项目后，首页正常显示，控制台没有错误；此项验证为本地启动检查，未执行真实设备扫码或真实支付。

设备端生成新二维码时应追加 `&v=1`；现有工作区没有设备端二维码生成源码，本轮实现接收、解析与路由，并提供 `buildDeviceQr` 构建工具及协议说明。上线时保留 `w.4mr.cn` 的小程序二维码打开规则，以及 `x.4mr.cn`、`checkin.voxel.cn` 两个 API 域名的 request 合法域名配置。

用户随后授权发布，并进一步限定旧 v0 支付不改、新 v1 支付修改。发布进度另记于根仓库 `docs/superpowers/plans/2026-10-23-mini-versioned-payments-release.md`；仅更新新后端，旧 `x.4mr.cn` 服务及原工作区的其他改动保留。
